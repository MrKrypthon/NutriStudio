## Cómo usar este documento en una sesión nueva

Al abrir una sesión nueva para seguir con el proyecto, en vez de "continúa donde lo dejamos":

> Lee `ESTADO_Y_PENDIENTES.md` y sigue con [nombre del pendiente].

Eso evita que la sesión tenga que releer módulo por módulo para saber qué ya está conectado — que fue la mayor pérdida de tiempo de esta sesión.

## Flujo de trabajo (para perder menos tiempo)

- **Una rama por tema, chica y revisable.** `fase-N-descripcion` para módulos nuevos, `fix-descripcion` para bugs encontrados sobre la marcha. Así ha sido hasta ahora y funciona; el problema no fue el tamaño de las ramas sino lo que sigue.
- **Instala `gh` CLI una vez.** Ahorita cada PR se crea a mano (Claude hace push y pasa el link de "crear PR", tú lo abres, apruebas y mergeas en GitHub). Con `gh auth login` una sola vez, Claude puede crear el PR directamente — un paso menos por fase, y evita el problema de abajo.
- **Mergea pronto, no dejes ramas abiertas mucho tiempo.** El fix de seguridad de `/tasks` (control de acceso roto) se hizo *después* de abrir el PR de Seguimientos, se subió a la misma rama, pero el merge en GitHub se quedó con el estado anterior — el fix no llegó a `main` hasta una rama aparte. Con PRs de vida corta esto no pasa.
- **Si tu `npm run dev:all` ya está corriendo, no lo toques — levanta uno propio en puertos distintos para probar.** Funcionó bien en la fase 9: `PORT=3002 node server/index.js` en segundo plano, y `VITE_API_URL=http://localhost:3002/api/v1 npx vite --port 5175` aparte. Comparten la misma base de datos, así que no hay nada que sincronizar, y al terminar solo hay que matar esos dos procesos por PID exacto (nunca `pkill -f "node server/index.js"`, que también mataría el tuyo si el patrón coincide).
- **No reinicies el servidor de desarrollo si no es necesario, y si lo levantas en segundo plano, apágalo al terminar de probar.** Reiniciar `npm run dev:all` para probar un solo endpoint nuevo se comió tiempo, una vez apagó por accidente la sesión de navegador que ya tenías abierta, y otra vez dejó un proceso vivo en el puerto 3001 que te impidió levantar tu propio `npm run dev:all` en tu terminal. Para probar solo el backend, `curl localhost:3001/api/v1/...` alcanza sin tocar nada del frontend.
- **Verifica en navegador contra el API real, no solo `npm run build`.** Así se encontraron los bugs reales de esta sesión (timezone, `Content-Type` en POST sin body, control de acceso, macros fijos en Recetas) — el build nunca los iba a atrapar.

## Rediseño Datta Able (fase 34 en adelante)

La usuaria pidió adaptar el diseño de la app a una plantilla que descargó: `datta-able-free-react-admin-template` (React + Vite + Bootstrap 5 + react-bootstrap, licencia MIT, carpeta en la raíz del repo pero **excluida de git** vía `.gitignore` — es material de referencia, no parte de la app). Es un proyecto de varias fases, no una sola: primero el chrome compartido (sidebar/topbar, usado por las ~30 pantallas), después cada módulo por separado.

**Decisión de arquitectura (fase 34):** la plantilla trae su propia maquinaria de React (Context de tema con RTL/mini-menú/header configurable, `react-router-dom` real, componentes `react-bootstrap`) y ~4,000 líneas de SCSS acopladas a esa maquinaria. Portar todo eso tal cual habría significado arrastrar infraestructura que esta app no necesita (no hay selector de tema RTL, no hay mini-menú) y, más importante, **arriesgaba filtrar estilos globales a las pantallas que todavía no se han migrado** — se encontró que `themes/_general.scss` de la plantilla tiene selectores sueltos como `p{font-size:14px}` que habrían afectado a toda la app de inmediato. En vez de importar el CSS de la plantilla tal cual, se extrajeron sus tokens de diseño reales (colores, medidas) de `settings/theme-variables.scss` y se aplicaron a mano dentro de la arquitectura CSS que ya existía en `globals.css` (variables `--green`/`--ink`/`--mint`/`--accent`, ya usadas por casi cada pantalla) — sin agregar Bootstrap ni ninguna dependencia nueva todavía. Esto se verificó con una captura antes/después mostrando que el renombrado de clases por sí solo no cambiaba nada visualmente, antes de aplicar el color real.

**Fase 34 — hecho:**
- `AppChrome.jsx` (sidebar + topbar) migrado a las clases `pc-*` de Datta Able (`pc-sidebar`, `pc-header`, `pc-link`, `pc-micon`, `pc-mtext`, `pc-caption`, `pc-badge`, `pc-nav-group`, `pc-sidebar-footer`) — mismo prop API externo (`active`, `setActive`, `children`), cero cambios en las ~30 pantallas que lo usan.
- Paleta real aplicada a las variables raíz existentes: `--ink:#1c232f` (sidebar/texto oscuro), `--green:#7267ef` (morado, ahora el acento principal en toda la app: botones `.primary`, badges, estados activos), `--mint:#eeecfd` (fondo suave del acento), `--accent:#ffa21d` (dorado, para el logo y detalles). ## Auditoría (fase 43)

El modelo `AuditEvent` (`practiceId`, `userId`, `action`, `entity`, `entityId`, `metadata` JSON, `createdAt`) existe desde el inicio del proyecto sin que ninguna ruta lo usara. Instrumentar las 56 rutas del API habría sido desproporcionado para el valor real — se acotó a las acciones que de verdad importan para trazabilidad clínica (quién hizo qué y cuándo sobre el expediente de un paciente):

- `PATCH /patients/:id`: si cambia `status`, registra `archived`/`reactivated`; si no, registra `updated` (edición de datos del paciente).
- `POST`/`PATCH`/`DELETE /consultations/:id/diagnoses`: `created`/`updated`/`deleted` sobre `Diagnosis`.
- `POST /plans/:id/publish`: `published` sobre `NutritionPlan`.
- `POST /documents/:id/deliver`: `delivered` sobre `Document`.

**Decisión de diseño:** `AuditEvent.entityId` es el id de la entidad auditada (el diagnóstico, el plan, el documento — no necesariamente el paciente), así que no sirve por sí solo para responder "dame los eventos de auditoría de este paciente". Cada llamada a `logAudit` guarda también `patientId` dentro de `metadata` (JSON), y la consulta lo filtra con `{ metadata: { path: ['patientId'], equals: patientId } }` — soportado por Prisma sobre Postgres. El registro es best-effort: `logAudit` atrapa cualquier error y solo deja un `warn` en el log, para que una falla de auditoría nunca tumbe la operación real que describe.

**Dónde se ve:** no se construyó una pantalla nueva — se integró directamente en la línea de tiempo que ya existía en el cajón de cada paciente (`GET /patients/:id/timeline`, que ya mezclaba citas/consultas/planes/documentos en un solo feed cronológico). Los eventos de auditoría aparecen ahí como una entrada más (`kind: 'audit'`), con una etiqueta legible por `entity`+`action` (ej. "Diagnóstico eliminado · Gabriela Alonso") y el nombre real de quién lo hizo. Verificado end-to-end: archivar/reactivar/editar un paciente y crear/editar/eliminar un diagnóstico contra una instancia aislada, confirmando por API que el filtro por `patientId` en JSON funciona y por Playwright que la línea de tiempo del paciente muestra las tres entradas de diagnóstico correctamente ordenadas, con ícono y atribución reales.

El upsert por nombre tenía un bug real, no solo una limitación cosmética: al iterar, la primera fila de origen con un nombre repetido consumía y borraba esa clave del mapa de "existentes", así que la segunda fila con el mismo nombre nunca encontraba su fila ya existente y creaba una nueva — **cada re-ejecución del script agregaba una fila duplicada más** para cualquiera de los 47 nombres que el Excel repite. El catálogo real había llegado a 3,048 filas (93 de más) antes de esta limpieza. Se investigó fila por fila: algunos nombres repetidos son duplicados accidentales genuinos del Excel (misma categoría, mismos datos — ej. "Aguardiente"), y otros son el mismo nombre listado en dos categorías o porciones distintas, con datos nutrimentales reales distintos (ej. "Doritos Nachos" a 20 g vs. 0.33 bolsita) — estos últimos NO son duplicados, son filas legítimas que había que conservar por separado. Se limpiaron las 69 filas que sí eran duplicado exacto (25 nombres colapsaron a 1 fila, 24 nombres conservaron sus 2 filas legítimas), verificado antes de borrar que ninguna receta referenciara las filas eliminadas (cero recetas afectadas). El script se corrigió para matchear por `(nombre, categoría, porción)` en vez de solo nombre — se probó re-ejecutándolo contra el catálogo ya limpio y dio 0 nuevos, 2871 actualizados, confirmando que ahora es realmente idempotente.
- **`server/domain/micronutrients.js` tenía las 6 llaves de nutrientes repetidas tres veces (tabla IDR, lista de labels, objeto de totales).** Al ampliar de 6 a 13 nutrientes en fase 17 se refactorizó para derivar todo de `NUTRIENT_LABELS`/`NUTRIENT_KEYS` en un solo lugar — evita que se repita la clase de bug de fase 15 (nutriente nuevo que se calcula en un lado pero se olvida sumar en otro). Si se agrega un nutriente más, solo hay que tocar `IDR_TABLE` y `NUTRIENT_LABELS`; también hay que sumarlo a `RECIPE_NUTRITION_KEYS` en `server/index.js` — son dos catálogos distintos (uno de metas, otro de qué se agrega a la receta) que siguen sin unificarse.
- **`prisma db push` casi borra la tabla `EducationMaterial` en fase 18.** Esta rama no incluye el modelo `EducationMaterial` (vive solo en la rama `biblioteca-educacion`, todavía sin mergear), pero la base de datos real sí tiene esa tabla con datos — todas las ramas de esta sesión comparten la misma base. `db push` compara el schema.prisma de la rama actual contra la base real y ofrece *borrar* cualquier tabla que no esté en ese schema. Para agregar `Measurement.abdomenCm` se usó `prisma db execute` con un `ALTER TABLE ADD COLUMN` en vez de `db push`. **Regla para las próximas fases: mientras haya ramas con modelos nuevos sin mergear, no correr `db push` sin leer con cuidado qué tablas propone tocar — un cambio de una sola columna puede pedir borrar una tabla completa de otra rama.**
- **`FormCard` (componente compartido del expediente) siempre convierte el último campo de la lista en un `<textarea>` de nota, sin importar qué tan corto sea el valor esperado.** Es la convención ya usada en "ICC calculado"/"Análisis de peso y talla" (correcto ahí, son campos de texto libre). Al agregar la tarjeta "Composición corporal" en fase 18 con `'Kg de músculo'` como último campo, ese número terminó en una caja de texto multilínea — cosmético pero además era justo el campo que lee `registerMeasurement`, así que valía la pena reordenar. Si se agrega una tarjeta nueva a `FormCard`, hay que decidir a propósito qué campo va al final (uno de texto libre) en vez de dejarlo por accidente en el último lugar de la lista.
